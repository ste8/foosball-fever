How the team generator works

A guide to how Foosball Fever picks the teams for a match day, starting from zero. It assumes no knowledge of graph theory. Every new term is explained the first time it appears, with a picture.

1. The problem

On each match day some players are attackers and the same number are defenders. Every team is one attacker plus one defender. The app's job is to choose the teams.

The goal is variety over a season. If Ale and Elena were a team last week, they should ideally not be a team again this week, or next week, or the week after. More precisely, the generator tries to answer:

What is the largest number N such that we can form every team without repeating any pair from the last N match days?

The app calls that number freshMatchDays. To find it, the generator combines three classic ideas, each explained below:

  • a graph, to describe who is allowed to team up with whom;
  • a matching algorithm (Hopcroft-Karp), to check whether a complete set of teams exists;
  • a binary search, to find the largest N quickly.

2. Graphs: dots and lines

In computer science a graph is nothing more than dots connected by lines. The dots are called vertices (or nodes) and the lines are called edges. It has nothing to do with charts or plots.

In our case each player is a dot. We draw a line between an attacker and a defender when those two are allowed to be a team. We never draw a line between two attackers or between two defenders, because a team always has one of each.

A graph whose dots split into two groups, with lines only going across the groups, is called a bipartite graph ("two parts"). That's our situation exactly: attackers on the left, defenders on the right.

3. Matchings: picking teams from the graph

Choosing the teams for one evening means choosing some of the lines, with one rule: each player can be on at most one chosen line. Nobody can be in two teams.

A set of lines that obeys that rule is called a matching. If every player ends up on a chosen line, it's a perfect matching, which is exactly a complete set of teams for the evening.

With all lines present, finding a perfect matching is trivial. The difficulty starts when some lines are missing, which is what history does.

4. Turning history into forbidden lines

To avoid repeating recent teams, the generator deletes the line for every pair that played together in the last N match days. Roles don't matter: if Ale defended and Elena attacked three weeks ago, that pair still counts as "played together".

5. Why the obvious approach gets stuck

The natural first idea is greedy: go through the attackers in order and give each one the first defender who is still free.

But 4 teams are possible: Ale–Elena, Bea–Luca, Carlo–Gio, Dani–Fede. Greedy failed because it never goes back to change an earlier choice. Bea could have taken Luca and left Fede for Dani, but greedy didn't know that when it gave Fede to Bea.

Trying every possible combination would fix that, but the number of combinations explodes: with 10 attackers there are 3,628,800 ways to pair them. We need something smarter.

6. The fix: augmenting paths

The smarter idea is to repair a stuck matching by reshuffling a few existing teams. The tool for that is the augmenting path.

Start from a player who has no team (Dani). Follow a chain of lines that alternates:

  1. an unused line from Dani to a defender (Fede),
  2. then the used line from Fede to her current partner (Bea),
  3. then an unused line from Bea to another defender, and so on,

until you reach a defender who is also without a team (Luca). That chain is an augmenting path. Click through it below.

Why does flipping always work?

  • The path starts and ends at players with no team, so the people at both ends can safely gain a partner.
  • Everyone in the middle loses one partner and gains another, so they're still in exactly one team.
  • The path has one more unused line than used lines, so flipping gives exactly one more team.
The key fact (Berge's theorem, 1957): if a matching is not as large as possible, an augmenting path always exists. So "keep finding augmenting paths and flipping them until none is left" is guaranteed to reach the largest possible matching. If that's smaller than the number of attackers, no complete set of teams exists.

That leaves one question: how do you find an augmenting path? That's a search problem, which brings us to BFS and DFS.

7. Searching a graph: BFS and DFS

There are two classic ways to explore a graph from a starting point. Picture yourself in a maze looking for an exit.

BFS: breadth-first search

Explore everything one step away first, then everything two steps away, then three, like ripples spreading in a pond. Each ripple is called a layer. Because you go layer by layer, the first time you reach a target you've found it by the shortest possible route.

BFS uses a queue (first in, first out, like a line at a shop) to remember which places to visit next.

DFS: depth-first search

Pick a direction and keep going as deep as possible. When you hit a dead end, step back to the last fork and try the next branch. This is called backtracking. DFS is simple and uses very little memory, but the first route it finds isn't necessarily the shortest.

DFS is usually written as a function that calls itself (recursion), or with a stack (last in, first out, like a pile of plates).

8. Hopcroft-Karp, step by step

The simplest matching algorithm just repeats: "find one augmenting path, flip it". That works. Hopcroft-Karp (named after John Hopcroft and Richard Karp, 1973) does the same thing in batches, which makes it faster on big graphs. Each round, called a phase, has two parts:

  1. BFS part: start from all attackers without a team at once and build the layers, as in the picture above. This tells us how long the shortest augmenting paths are, and gives every attacker a layer number.
  2. DFS part: for each free attacker, dive through the layers, always moving to the next layer (never sideways or back), looking for a free defender. Each path found is flipped right away. Players already used by a path in this phase can't be reused, so the paths found in one phase never overlap.

Phases repeat until the BFS part can't reach any free defender. At that point there are no augmenting paths left, so the matching is the largest possible. Here's the whole run on our example:

Notice that phase 1 behaves exactly like greedy: with no teams yet, the shortest augmenting paths are single lines. Phase 2 is where Hopcroft-Karp beats greedy, by finding the longer path that reshuffles Bea.

Why bother with batches?

One path at a time can take as many rounds as there are players. Hopcroft-Karp proved that with batching, the number of phases is at most about √(number of players), so the total work grows like E × √V, where E is the number of lines and V the number of players. For a foosball group of 10 to 30 people this difference is invisible (both take microseconds), but it's the standard, well-tested choice, and the code ported it from the C# version.

In the code (hopcroftKarp.ts): bfs() is the BFS part and fills dist[] with each attacker's layer. dfs(u) is the DFS part and only follows a line when dist[next] === dist[u] + 1 (the "always move to the next layer" rule). pairLeft[] and pairRight[] store who is partnered with whom. When a DFS gives up on an attacker it sets dist[u] = Infinity, so the same dead end isn't explored twice in one phase.

9. Binary search: how many match days to avoid

Hopcroft-Karp answers a yes/no question for one value of N: "if we avoid the last N match days, is a complete set of teams possible?" To find the largest N that says yes, we could try N = 1, 2, 3, … until it fails. Binary search gets there in far fewer tries.

The property that makes it possible

Avoiding more match days only ever removes lines, never adds them. So if N = 7 is impossible, N = 8, 9, 10 are impossible too. The answers look like yes, yes, yes, …, yes, no, no, …, no, with a single switch point. Binary search is the standard way to find a switch point.

How it works

Keep a range of candidate values (lo to hi). Test the middle one. If it works, the answer is at least that, so throw away the lower half. If it fails, throw away the upper half. Each test halves the range, like guessing a number between 1 and 100 by asking "higher or lower?".

10. Randomness and seeds

Often there are many different complete sets of teams that are all equally fresh. Which one Hopcroft-Karp returns depends on the order in which it looks at each player's lines. To get variety, the generator shuffles every player's list of lines before matching, using the standard Fisher-Yates shuffle.

The random numbers come from a tiny generator called mulberry32, which starts from a number called the seed. The same seed always produces the same sequence of "random" numbers, so the same input and seed always give the same teams. That makes the tests repeatable. The app picks a new random seed every time you press Generate.

11. Putting it all together

This is what generateTeams() in generateTeams.ts does from start to finish:

Check the input validate(): same number of attackers and defenders, no duplicates, nobody in both roles
↓
Number the players and list each past match day's pairs precomputeForbiddenPairs(): one list per match day, most recent first, both role orders included
↓
Binary search over N (section 9). For each N tried:
Build the graph without the pairs from the last N match days tryMatchAtDepth() and BipartiteGraph
↓
Shuffle each player's lines with the seed graph.shuffle(rng) (section 10)
↓
Run Hopcroft-Karp. Is everyone in a team? hopcroftKarp() (section 8). Yes: remember these teams and try a larger N. No: try a smaller N.
↓
Return the teams from the largest N that worked, plus statistics freshMatchDays = that N; repeatedCount = how many teams have played together at any point in the history; lastOccurrence = for each team, how many match days ago they last played together

Where it runs in the app

The match day setup screen runs generateTeams() in a Web Worker (a background thread), so the screen stays responsive. If you press Stop, or the worker hasn't finished after 5 seconds, the screen runs it again directly on the main thread and uses that result. In practice the worker finishes long before either happens.

12. Known limitations

  • Older repeats aren't minimized. Once N is fixed, any complete set of teams that avoids the last N match days is accepted. One choice might repeat a pair from N + 1 match days ago while another repeats nothing, and the generator treats them as equally good. Fixing this would mean replacing "yes/no matching" with a minimum-cost matching (for example, the Hungarian algorithm), where repeats cost more the more recent they are. You can see this in section 4: at N = 2 the demo's teams repeat two pairs from match day 1, although a lineup that repeats only one exists (Ale + Luca, Bea + Fede, Carlo + Elena, Dani + Gio).
  • No partial results. The worker only reports when it's done. Stop doesn't return a "best so far". It starts over on the main thread with a fresh seed, which is still fast at this scale.
  • N = 0 is solved twice. The code solves N = 0 before the binary search as a fallback, and the binary search may then test 0 again. It's harmless, just a little redundant.

13. Glossary

TermMeaning here
GraphDots (players) connected by lines (allowed teams).
Vertex / nodeA dot, meaning one player.
EdgeA line, meaning one possible attacker + defender team.
Bipartite graphA graph split into two groups (attackers, defenders) where lines only go across the groups.
MatchingA set of lines where nobody appears twice: a valid (maybe incomplete) set of teams.

PhaseOne round of Hopcroft-Karp: a BFS to build layers, then DFS to flip several shortest augmenting paths.

Binary searchFinding a switch point by repeatedly testing the middle and discarding half the range.
